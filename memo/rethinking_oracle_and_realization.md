# 再考 : oracle と realization

## 再考に至るまでの経緯

oracle file をエージェントに代理で編集させる方法は、まぁまぁ上手く機能している。
人間意図をプロンプト経由で与えて、それを「既存仕様と整合するように注意深く反映する」のはエージェントという役割分担が実現している。
しかし、これにはまだいくつかの問題が存在する。

- エージェントが生成した冗長な仕様書（ワードサラダ）を読むのが大変すぎて、人間の認知能力を浪費させられる（ただでさえ貴重なのに！）
- 編集後の oracle file は「人間意図」と「エージェントが補った隙間」とが混ざってしまって、それらをあとから判別することが出来ない
- 判別ができないから、cmoc の仕組み上は oracle file 全体を「動かせないゴールポスト」として扱うしかない（人間意図がエージェントに汚染される）
- oracle file の品質を担保しなければならないが、自然文章の品質は抽象的で評価が難しい
- 「開発対象リポジトリのことを人間がよく知っている」という背景があまりにも強力すぎて、いろんな問題がマスクされて潜んでそう

cmoc 開発フロー上の最大のボトルネックは「oracle file 編集作業に必要な人間の認知能力の枯渇」なので、最優先でケアするべき箇所である。
しかし、小手先の変更でどうにかなる気もしないので、根本的な再考を行う。

## 前提の整理

今はというと、以下の方針を採っているため、エージェントによって oracle file を人間好みの品質に保てるのが最も望ましい。

- oracle file は Markdown による自由記述
- oracle file を直接的に編集するのはエージェント
- 人間も oracle file を読めたほうが本当は良い

しかしながら、以下の事情から、エージェントの成果物の品質をプロンプトで制御するアプローチは筋が悪い。

- エージェントはとにかくモリモリ仕様の隙間を埋めて well defined にしようとする傾向がある
- この傾向はもはやモデルの基本的性質 (解釈の余地を利用して最大限サボる) であり、プロンプトで調整したくてもなかなか言うことを聞いてくれない
- ファイル・観点毎にエージェントを起動すれば言うことを聞いてくれる度合いは上がるかもしれないが、あくまで程度の問題であり根本的解決ではないし、消費トークン数がエグすぎる
- そもそも「well defined にするな」的な事を解釈の余地のない状態で自然言語的に定義すること自体が困難
- 大量に指示を書くと逆に作業品質が落ちるという話もあるので、できれば長々と書きたくはない

## アプローチ：oracle, realization --> decision, spec, realization

そこで、リポジトリ全体を oracle, realization に区分したように、oracle を decision, spec に区分することで、人間意図がエージェントによる汚染から隔離・保護される事を狙う。

decision 

- 明文化された人間の意図（決定事項）を書く
- 100% 人間が編集する
- 別の言い方をすれば、仕様断片
- 具体的には、期待する状態の自然言語での定義
- ある意味、テストとその期待値を書くようなノリ
- ある意味、初期コンセプトである「oracle file は 100% 人間が書く」がここに復活した
- 本当に最低限の意図・判断だけを短く簡潔に書く想定で、書く量で言えば「プランの提示をプロンプトで指示する時」くらいの温度感

spec

- decision を元に生成された仕様文章
- こちらは断片ではない仕様書
- 「どのような仕様書であるべきか？」については口うるさく書かず、エージェントの好きにさせる
- 100% エージェントが編集する

realization

- spec を元に生成された実装・テスト・などなど
- decision, spec どちらでもないもの
- 「どのような実装であるべきか？」については口うるさく書かず、エージェントの好きにさせる
- ここは以前の仕様から据え置き

## decision の記述方法

以下のような書式の markdown が記述されたファイルを decision ファイルとする。

```markdown
# [DEC-000000] 決定事項（あ）

ほげほげ

# [DEC-000001] 決定事項（い）

ぴよぴよ
```

なお、

- decision ファイルは `{{work-root}}/decision/**/*.md` として配置される
- decision ファイルは複数存在してよいし、1 つの decision ファイル内に複数の decision が記述されていても良い

### 人間が矛盾のない decsion を書くのって結構大変では？

decision を十分に疎に保てば、現実的な手間で「矛盾のない仕様断片」に保てるはず。
逆に言えば、人間が decisino をメンテナンスしきれる能力をもっているかどうかに強く依存していることになる。
decision を手放す＝人間によるディレクションを手放すということなので、ここは絶対に手放せない。
よって、この問題は割り切って受け入れるしか無い。

### 「人間が開発対象リポジトリのことをよく知らないといけない」は何も解決しないのでは？

人間がスジの良い判断を下せるかどうかは、人間のリポジトリに対する理解度に強く依存する。
`cmoc work plan` の説明ベースで判断することになるので、ある程度はエージェントにカバーしてもらえるが、根本的解決ではない。
これは元々あった問題であり、decision 方式で悪化しているわけでもないので、このまま受け入れる。

### oracle file 方式と何が違う？

oracle file には「人間の意図」と「エージェントが埋めた隙間」とが混ざっていた。
そのため、後から oracle file をシンプル化しようと思っても、消して良い要素と消してはいけない要素との区別が付かないので、シンプル化の余地が実質無い。

それに対して decision, spec では「人間の意図」と「エージェントが埋めた隙間」とが完全に分離している。
そのため、後から oracle file をシンプル化しようと思ったら「decision に反しない範囲で spec を好きにしていいよ」に出来るので、シンプル化の余地が存在するはず。
「実は大事なことが decision で宣言されていませんでした」があるとシンプル化によって大事な事が消えてしまうことになるが、これは「失って初めて気づいた大事なことを改めて decision に書く」でカバー可能。
どのようにカバーすればよいかが分かっている点で oracle file 方式よりも優れるだろう。
