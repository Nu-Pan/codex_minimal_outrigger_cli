# 再考 : oracle と realization

## 再考に至るまでの経緯

oracle file をエージェントに代理で編集させる方法は、まぁまぁ上手く機能している。
人間意図をプロンプト経由で与えて、それを「既存仕様と整合するように注意深く反映する」のはエージェントという役割分担が実現している。
しかし、これにはまだいくつかの問題が存在する。

- エージェントが生成した冗長な仕様書（ワードサラダ）を読むのが大変すぎて、人間の認知能力を浪費させられる（ただでさえ貴重なのに！）
- 編集後の oracle file は「人間意図」と「エージェントが補った隙間」とが混ざってしまって、それらをあとから判別することが出来ない
- 判別ができないから、cmoc の仕組み上は oracle file 全体を「動かせないゴールポスト」として扱うしかない（人間意図がエージェントに汚染される）
- oracle file の品質を担保しなければならないが、自然文章の品質は抽象的で評価が難しい
- 「開発対象リポジトリのことを人間がよく知っている」という背景があまりにも強力すぎて、いろんな問題がマスクされて潜んでそう

cmoc 開発フロー上の最大のボトルネックは「oracle file 編集作業に必要な人間の認知能力の枯渇」なので、最優先でケアするべき箇所である。
しかし、小手先の変更でどうにかなる気もしないので、根本的な再考を行う。

## アイディア・アプローチ

### oracle file を decision list で置き換える

前提として、今は、

- oracle file は Markdown による自由記述
- oracle file を直接的に編集するのはエージェント
- 人間も oracle file を読めたほうが本当は良い

であるため、エージェントによって oracle file を人間好みの品質に保てるのが最も望ましい。

しかしながら、

- エージェントはとにかくモリモリ仕様の隙間を埋めて well defined にしようとする傾向がある
- この傾向はもはやモデルの基本的性質 (解釈の余地を利用して最大限サボる) であり、プロンプトで調整したくてもなかなか言うことを聞いてくれない
- ファイル・観点毎にエージェントを起動すれば言うことを聞いてくれる度合いは上がるかもしれないが、あくまで程度の問題であり根本的解決ではないし、消費トークン数がエグすぎる
- そもそも「well defined にするな」的な事を解釈の余地のない状態で自然言語的に定義すること自体が困難

であるから、エージェントの成果物の品質をプロンプトで制御するアプローチは筋が悪い。

そこで、oracle file を一定のスキーマに従う構造化データ化し、スキーマ上の要素毎に、人間・エージェント・機械的編集の役割分担（所有者の定義）を行い、人間の所有物をエージェントによる汚染から隔離することで、「自然言語文章の品質を人間好みに保つ必要がある」という問題の消去を図る。
発想としては、oracle, realization に分離して realization を全くレビューしないようにしたのと同じで、oracle file をさらに細かくブレークダウンしようという話である。

### decision list の構造

具体的には、oracle doc を decision のリストという形式に置き換える。結果的に、`DECISION.md` みたいなアプローチになった。

dicision は１件１ファイルで管理する。
パスは `{{work-root}}/decision/{{owner}}/{{ID}}.md` で管理。
`{{owner}}` は `HUM`, `AGT` の２択。
`{{ID}}` は 6 ケタ。

decision はメンバーとして ID を持つ。
ID は `DEC-{{owner}}-XXXXXX` の形式。
cmoc 全体共通の ID 規則の拡張が必要かも。

decision のメンバーは「ID、本文、参照」だけ。ただし、decision には所有者の概念が存在し、人間が所有する場合は human decision に、エージェントが所有する場合は agent decision に分類され、分類ごとに事情が全く違う。

**human decision**

- 100% 人間が書く
- 本質的には、人間が手書きする意図・判断
- 具体的には、期待する状態の自然言語での定義
- ある意味、テストとその期待値を書くようなノリ
- ある意味、初期コンセプトである「oracle file は 100% 人間が書く」がここに復活した
- 本当に最低限の意図・判断だけを短く簡潔に書く想定で、書く量で言えば「プランの提示をプロンプトで指示する時」くらいの温度感

**agent decision**

- 100% エージェントが書く
- エージェントが仕様ドメイン上での作業中に置いた仮定
- 別の言い方をすれば、エージェントが勝手に決めた仕様
- あるいは、仕様で定義せずに実装者裁量に任せることを明示する
- human say と重複する内容を記述してはいけない
- ある意味、今まで TUI 上でエージェントに提示させていた「プラン」がこれに相当する

### decision list に対する読み書き操作も構造化する

oracle, realization と同様、dicision に対する読み書き操作も構造化する必要がある。

情報の流れは「human --> `DEC-HUM-XXXXXX` --> `DEC-AGT-XXXXXX` --> implementation --> feedback issue --> human --> ...」という循環構造とする。

エージェントの種類を以下のように定義する。

- decision read agent
    - decision ドメイン上での非書き込み作業を行うエージェント
    - realization に対する読み書き禁止 (逆流阻止)
    - human decision, agent decision 対する書き込み禁止
- decision write agent
    - agent decision の編集作業を行うエージェント
    - realization に対する読み書き禁止 (逆流阻止)
    - human decision に対する書き込み禁止 (逆流阻止)

これらを踏まえた上で、追加・変更・削除どのケースでも、以下のワークフローとする。

1. 人間がやりたいことを cmoc の UI から入力
    - 追加したい human decision 本文
    - 変更したい human decision の ID と、変更後の本文
    - 削除したい human decision の ID
    - これら操作のセットを UI から入力する
2. この「やりたいこと」に対して、エージェントと人間とでプランを揉む
    - 既存 human decision との整合性をエージェントが評価して人間に返す
    - どのように decision 全体の整合性を取るのかのプランを decision read agent に提示させる
    - 気に入らない所があれば、1. に戻って操作セットを修正する
3. 合意できたプランに基づいて human decision の追加と agent decision の修正作業を行う
    - human decision 間の隙間を agent decision で埋める
    - ここは固定処理 (現行で言う `cmoc oracle edit` に相当する)
    - エージェントから人間への問題点の報告は feedback issue の仕組みを使う

これは、feedback issue の観点では、元々「realizatino file 側で様々な問題を受け止める」だったのが、「decision 上で問題をできるだけ受け止めて、その上で realization 側でも問題を受け止める」という２段構成になった、と解釈出来る。

### エージェントから decision へのアクセスを仕組み化する

stdio MCP server 経由でのアクセスとする。

- 検索
- 読み
- 追加
- 変更
- 削除
- 現在の差分の列挙

### 人間用の編集 UI を作り込む

- 今は codex でプランを提示させてそれを人間が読んでいる (oracle file を直接読むことはない)
- これを「都度ビューを作らせている」と捉えるると「その場その場の事情に応じてビューを作ってもらわなければ、人間はまともに判断を下せない」ということでもある
- であれば、ここは割り切って「都度ビューを作る」とその周辺の UX を真面目に設計する価値がありそうだ
- 今までは CLI でやっていたが、ここで初めて web サービス的なフロントエンドを作る動機が生えてきた (CLI + Markdown は読みづらいという話は元々あったけどね)

## 懸念点

### 人間が矛盾のない human decsion を書くのって結構大変では？

- oracle file の頃に「人間が書くのは無理」になったのは、エージェントが「本当に必要最低限だけを oracle file に書く」を守らずに、well defined な仕様文章に育て上げたことが原因
- それに対して decision では、面倒な話をエージェントに丸投げしたら agent decision にしわ寄せが行くように最初から設計されているので、human decision が汚染されてメンテ不可能っていうルートは無いはず
- 人間が human decision をグズグズにしてしまうルートについては、やってみないと分からないので現時点では考える必要はない
- 実際にやってみて知見を集める価値はありそう

### 「人間が開発対象リポジトリのことをよく知らないといけない」は何も解決しないのでは？

- 人間意図を human decision に隔離しようとも、適切な判断をするためには agent decision の確認も必要
- これってつまり「結局は人間側の理解度を上げないとダメだよね」と言っているに等しい
- 「人間が開発対象リポジトリの事をよく知っていると生産性が向上する」と「人間が開発対象リポジトリの事をよく知らないと開発が成立しない」は別の話で考えるべきだろう
    - 生産性の向上は、人間側の成長による＋αなので、シビアに考えなくていい
    - 開発が成立しないのは地名てきなので、シビアに考えたい
- 結局「都度エージェントに human decision, agent decision を説明してもらいます」でケアされるのだから「開発が成立しない」までは行かないのでは？
- ここは比較的楽観視して良さそう

### oracle file 方式と何が違う？

- 人間側の理解度の問題をケアするために「都度エージェントに human decision, agent decision を説明してもらいます」とするなら、oracle file 方式と何が違うのだろうか？
- oracle file 方式では「ファイル <--> エージェント <--> 人間」という透過的操作だったので、ある意味責任分担がわかりやすかった (そのシンプルさ故に、エージェントに負わせる責任が広くなりすぎた)
- それに対して decision 方式では、「人間が読む」方向の操作については今までと同じだが、「人間が書く」方向の操作については細分化がされたとことになる
- 恐らく、ここの「細分化された」が曖昧なまま放置されているのが問題

### agent decision は第二の oracle file になるのでは？

- agent decision と oracle file はその性質がとても近い
    - 読み書きはエージェントの仕事で、人間はエージェント越しに間接的に関与する
    - これだけ聞くと、同じに見える
- 明確な違いが 1 つ存在する
    - 重要な人間意図は human decision に隔離されているはず
    - 隔離前提が守らているならば agent decision はどのように書き換えても人間意図に反することはないはず
    - だから、エージェントに対して「既存 agent decision の維持」を指示する必要が無い
    - これは「そのその場の最適を目指してほしい」ととても良く整合する

### agent decision のメンテンス問題が現実的に解決可能になってしまうのでは？

- 今までは oracle file というデカい括りなので、実質的には解決不能として諦める事がきでた
- しかし、agent decision として構造化されてしまうと、エージェントによる自動メンテナンスができそうな気がしてしまう
- 実際成立しそうか？
    - 「human decision 同士の隙間を埋めるのに必須（ミッシングリンクの解決に必須）であるものだけを agent decision として残す」という目標に設定出来る
    - 停止性は怪しいが、反復的な最小化問題っぽい形式にはできそう
    - 今の `cmoc realization refactor fork` みたいな、停止しない前提の反復的改善操作には落とし込めそう
- 時間を実用範囲内に収められるか？
    - 今の `cmoc realization refactor fork` と同程度には出来るだろう
    - 今は oracle file の路線を継承して gpt-6-astra の想定なので、遅いってことは無いはず
    - 多分、問題ではないだろう
- コストを実用範囲内に収められるか？
    - Astra は高いのでかなり不安がある
    - 人間とエージェントとで完全な棲み分ける前提なので gpt-6.1-sol に落として日本語能力の終わりっぷりを踏み倒すという手はある
    - System 1 decision model は、後続への悪影響を考えると流石に無理
