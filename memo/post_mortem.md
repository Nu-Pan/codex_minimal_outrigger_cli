# 全く同じタスクを２回繰り返す

当時 gpt-5.6-sol だった頃は、「よく定義された仕様書を渡したから、エージェントが仕様書と実装をよく読んで比較すれば、仕様通りの実装になるはず」みたいな問題設定を与えた場合、１回の作業では抜け漏れが発生する傾向があり、現実には「様々な開発作業をこなしていく過程でちょっとづつ穴が埋まり、最終的には完璧な状態に漸近する」という感じだった。しかし、それはつまり「この問題はすでに解決済みだと思ったけど実は解決してなかった」が発生するということであり「管理上の把握している現在の状態と、実装上の現在の状態がズレる」ということになる。このズレは、当然ながら後続の作業に悪影響を与えるし、こういった問題は小さいうちに安く解決するべきである。

そこで、全く同じ作業を複数回エージェントに依頼するという対策を取った。エージェントに与える指示に冪等性（作業後に満たすべき目標状態だけを定義して、現状をそれに合わせることを依頼する。現状と目標がずれていれば普通に作業をするし、ズレがなければチェックだけが行われるはず。）を持たせて、全く同じ作業を複数回実行させる方式とした。

gpt-5.6-sol 当時は実際に効果があった。最初は意味のある差分が発生するが、繰り返すごとに無意味な差分に漸近していく傾向があり、経験的に２～３回程度の反復が妥当という結論に至った。

gpt-6-astra では反復しなくても 1 回で完璧な結果が得られるようになったが、それでも２回目の実行の「コンテキスト的にクリーンな状態で１回目の作業結果が妥当であると評価した」は担保として意味がある。

# 文章ルーティング

エージェントが作業に必要な文章を特定する（ルーティング）のための仕組みとして、各文章の説明を書いた `INDEX.md` という仕組みを cmoc 開発最初期から運用していた。というか、cmoc を作る動機となったのはこの「ルーティング文章を機械的に正しい状態に保つ」が欲しかったから。

この `INDEX.md` が無い状態の開発を知らないので、これに効果があるかどうかは正直分からない。一方で問題は現実に発生していて「この `INDEX.md` はコスパモデルで機械的に生成するものであり、メイン作業をやっている時に編集するものではない」をエージェントに教える必要があって、これは当然コンテキストウィンドウを圧迫するし、余計な仕事を増やすのも良くない。`INDEX.md` の内容を生成するのにも codex を使うわけだが、これに最低でも数分はかかる（Reasoning Effort を下げれば品質は上がるが、待ち時間も伸びる）ので、待ち時間が長過ぎるて開発体験的に良くない。さらに致命的な問題として「feedback issue に `INDEX.md` の問題を何度も報告する」が起きてしまった。呼び出し回数がとても多いので、`gpt-5.6-luna` と好相性で喜んでいたのだが、現実は厳しい。

そもそも、ルーティングが必要であるとする積極的な理由があまり見当たらない。
（特に最新世代のモデルは）キーワード検索を巧みに使って必要な文章を特定するので、補助的なルーティング情報は絶対に必要という程ではない。
「関係する記述への参照を文章内に書くこと」という規定を入れておけば、関係ファイルは結構正確に列挙してくれる。
ソースコードについてはそもそもキーワード検索との相性が良いし、そうでなくても静的解析ツールで関係箇所を機械的に列挙出来るし、なによりも「AI が書いた壊れやすいテストが、実際に壊れることで関係箇所を教えてくれる」のが大きい。

それはそれとして、関係文章の列挙は大抵ワークフローの上流であり、上流でミスが起こると下流で致命的な問題として表面化する危険性があるから、ルーティングに補助を入れておきたいという動機そのものは間違いなくある。

GPT-6 登場くらいのタイミングで、`INDEX.md` を廃止して、ベクトル検索に乗り換えた。仮説としては「キーワード検索は表記揺れに弱いが、ベクトル検索は多少ワードが違っても意味の近さでヒットする。相補的な関係なので、ベクトル検索は補助として適切であろう。」といったところ。

ベクトル検索は運用し始めてまだ日が浅いが、今のところは良好。初回だけは埋め込みの全構築に時間がかかる（ローカルで CPU 推論しているのでしょうがない）けど、それ以降はかなり短い時間で済む。

ベクトル検索機能の実装は QMD を入れておしまいみたいな簡単は話ではなかった。エージェントに提供する機能（契約）に問題があったため、cmoc 独自実装にして細かいところを詰める必要があった。とはいえ、既に存在するものの移植なので、初回実装は割とすんなりいった（その後の機能を詰めていくフェーズは大変だった）。

# ワークフロー分離

cmoc のワークフローは概ね以下の段取り

1. `cmoc tui` で事実関係・実装レベルの実現可能性の調査
    - 省略可
    - 人間の「〇〇したいと思ってるんだけど」が無茶な話ではないかを最初にチェックする
    - ここは oracle file, realization file 共にアクセス可能
    - 必要ならモデルが `/tmp` 内で実証実験を行ったりする
2. `cmoc oracle investigation` で仕様プランを提示させて揉む
    - 省略可
    - 人間がプランを書くのはコストが高いけど、AI が書いたプランを読んで判断するのは安い
    - AI に人間の意図が正しく伝わっているかを、提示プランを読んで判断
3. `cmoc oracle edit` で oracle file に仕様変更を適用
    - oracle file の編集作業は AI に任せる
    - 修正プランが OK なら、修正作業も自動的に OK になるという建前だが、実際には伝言ゲーム (handoff) でズレが起きる
    - `oracle src` だけは真面目にレビューする
4. `cmoc realization apply fork` で変更した仕様を実装に反映
    - `realization file` を `oracle file` の最新の状態に追従させる
    - `realization file` の差分は一切レビューしない

# セッション間の handoff

ワークフロー上のセッションをまたぐ時、次のセッションへの引き継ぎを人力で書くのはダルい。
ということで、引き継ぎ前のセッションに「このセッション内で合意した内容を元に、次のセッションに作業を handoff して下さい」みたいな事が出来る仕組みを作った。

handoff の「楽をしたい」の部分はかなり良い手触り。しかしながら、本質的には伝言ゲームなので作業品質に対する不安はある。実際、handoff 時に意図がドリフトしていたケースが 1 度だけあった。

# AI による仕様書の編集

何も無い所からのポン出しはかなり良いものが出てくる。
が、そこから継続的にメンテナンスしだすと、ヤバいことになる。

モデルがあれこれ過剰に書こうとする傾向は、以下の施策でかなり改善した

- 仕様書を編集する作業では、実装の閲覧を禁止する
    - 仕様レベルで気にする必要が無いようなディティールの話を仕様に大量に書こうとする傾向がある
    - これは「実装が仕様に漏れ出している現象」であると仮定
    - そもそも実装を見せなければ、漏れ出すこともないよねということで閲覧禁止にした
    - たまに油断して区分なしの実行 (`cmoc tui`) をすると痛い目に遭う (gpt-6-astra でも変わらない)。
- 「実装者裁量」の概念を言及・尊重させる
    - 「ここまで言えば後は分かるでしょ」だけを oracle file に書きたい
    - 「後は分かる」の言語化として「実装者裁量」が良かった
- 関係する記述への参照を書かせる
    - あちこちで意味的に同じ仕様を重複記述する傾向があった
    - これは「既にあるということに気づかずに、別のところに同じ事を書いてしまう」であると仮定
    - 「〇〇については✕✕を参照」みたいな参照情報が網羅的に整備されていれば、それがモデルの目に入るのだから、既にあるということに気づけるはず

しかし、それでもモデルの根本的な性質の壁は乗り越えられなさそう。
仮説としては「AI が必要なもの・必要ないものを判断するために必要な文脈を与えられていない」とか「モデルのポストトレーニング上において、要らないものを足しても減点されないから、とりあえず足しとけばいいやと学んでしまった」とか。

別の話として、生成されたコードの品質も基本的に終わっている。
