## 1. 目的と設計上の判断

目的は、エージェントが必要な仕様へ到達しやすくすること。QMD が検索候補を返し、エージェントが結果を手がかりに現在の worktree の実ファイルを読む。

```text
エージェントが問いを作る
    → QMD で候補を探す
    → エージェントが原文を読む
    → 判断・追加調査・編集・検証を進める
```

cmoc が事前に「今回の作業に必要な地図」を選んで注入する方式にはしない。検索用の索引を事前作成することと、読むべき内容を事前選択することは別である。

QMD に調査全体を委任するのでもない。問いの分解、追加検索の判断、規定の解釈、作業結果への責任は、既存の cmoc エージェント側に残す。

### 合意した方針

- QMD は追加の探索手段として使う。原文の直接参照、文字列検索、既存の INDEX.md を直ちに廃止することは目的にしない。
- エージェントとの接続は **stdio MCP**。HTTP MCP は、エージェント内で cmoc をテストする際のサンドボックス制約に合わないため採用しない。
- 埋め込みに **Qwen3-Embedding-4B**、再ランキングに **Qwen3-Reranker-4B** を採用する方向で進める。
- 検索語の作成・言い換えは既存エージェントが担当する。QMD の独立したクエリ展開モデルを必要構成にしない。
- 導入判断のための cmoc 専用ベンチマークは新設しない。既存の公開評価を根拠に採用し、実装に必要な動作・互換性確認を行う。

### 今回は採らない方向

graphify 等のグラフ基盤、ChunkHound 型の調査エージェント、独自の検索エンジンやモデル学習、共有推論サーバーは、今回の導入に抱き合わせない。これらが一般に無価値という判断ではなく、今回の目的と工数に対して責務を広げすぎないためである。

## 2. 既存評価から見込める効果

### 2.1 エージェントへの補助検索追加

Cursor の公開比較では、同じモデルに意味検索を利用させる条件と、従来の検索手段だけを利用させる条件を比較し、コードベース質問応答の正答率が平均 **12.5%改善**したと報告されている。実利用での生成コード保持率は全体で **0.3%改善**、1,000ファイル以上のコードベースでは **2.6%改善**。数値は記事の `%` 表記に従い、パーセントポイントへの換算はしない。[B1]

これは Cursor 独自の検索基盤による評価であり、QMD や cmoc の測定ではない。検索中心の作業で効果が大きく、検索不要の作業も含めた全体では効果が薄まる、という期待の置き方に使う。

### 2.2 Agent Retrieval Bench が示す補完性

Agent Retrieval Bench の287課題における Codex GPT-5.4 の探索軌跡と検索結果の比較では、Qwen3-Embedding-8B の上位20件には正解があるが、エージェントが到達しなかった課題が **16.7%**。逆に、エージェントは到達したが検索上位20件には入らなかった課題も **10.1%**あった。[B2]

これは検索ツール追加による成功率向上の実測ではなく、両者の結果を照合した補完性の観測である。検索器だけに置き換えるより、既存の探索を残して検索経路を増やす方針を支持する。

### 2.3 cmoc に対する見込み

期待するのは、所在不明の仕様、用語が一致しない規定、領域をまたぐ制約への到達改善である。対象ファイルが既に分かる局所変更や、必要な仕様を読んだ後の設計・実装能力には、直接の改善を期待しない。

**全体としては小幅な品質改善、探索中心の作業ではそれより大きい改善を見込む。** これは既存評価からの設計判断であり、cmoc の成功率を具体的な数値で予測したものではない。トークン半減、実行時間短縮、INDEX.md の維持費削減は、今回の導入だけで得られる便益として計上しない。

## 4. 構成案：stdio MCP と再利用する索引

```text
cmoc
  ├─ call の work-root と閲覧可能範囲を確定
  ├─ 対応する QMD 設定・索引を準備／更新
  │
  ├─ Codex call A
  │    ├─ stdio ── 既存の cmoc MCP
  │    └─ stdio ── QMD process A
  │                  ├─ Qwen3-Embedding-4B
  │                  ├─ Qwen3-Reranker-4B
  │                  └─ 対象 worktree・閲覧範囲の索引
  │
  └─ Codex call B
       └─ stdio ── QMD process B
                         └─ 同一 worktree・同一範囲なら同じ索引を再利用
```

QMD の stdio MCP は `qmd mcp` で起動できる。cmoc がサーバーを先に常駐させるのではなく、cmoc が渡した MCP 設定に基づいて Codex が子プロセスとして起動する構成を基本案とする。[Q1][Q3]

単位は論理的な agent call 全体ではなく、個々の **Codex call／process**。同一 process 内では検索ごとに起動し直さず、終了時に QMD も終了する。索引は次の呼び出しでも使う。

この起動単位は、現行 cmoc の feedback が Codex call ごとの local stdio MCP を使う構造と整合する。ただし、feedback collector 自体に検索責務を追加する必要はない。[C3]

**共有するものは索引とモデルファイルであり、ロード済みモデルの実行時メモリではない。** HTTP サーバー、ポート管理、stdio から HTTP へ転送するブリッジは導入しない。

## 5. エージェントとの責務分担

### 5.1 cmoc が担当すること

対象 worktree と許可された検索範囲の確定、QMD 設定と保存先の準備、索引更新の調停、Codex への MCP 設定注入を担当する。検索アルゴリズム、独自の文書要約器、追加の調査エージェントは実装しない。

### 5.2 QMD が担当すること

本文の索引化、キーワード検索、埋め込み検索、順位統合、再ランキング、候補と原文位置の返却を担当する。本家 QMD の既存機能を利用する。[Q1][Q3]

### 5.3 エージェントが担当すること

何を知る必要があるかの判断、検索語の生成、候補の選択、原文の読解、追加調査、作業結果への反映を担当する。

検索結果のスコアや短い抜粋を仕様の正本として扱わない。対象 worktree の実ファイルを開き、必要な節や前提まで読む。索引に保存された本文と実ファイルの状態が異なる場合、古い索引を判断の根拠にしない。

## 6. 検索インターフェースと設定の具体像

### 6.1 自動クエリ展開は使わない経路を選ぶ

確認した QMD MCP の `query` ツールは、単純な `query` 文字列と、型付きの `searches` 配列を受け付ける。両者は排他的で、前者は内部モデルによるクエリ展開を行い、後者は呼び出し側の検索要求を直接実行する。[Q3]

今回使うのは **`searches`**。基本は `vec` と `lex` を使い分ける。HyDE は利用可能だが初期構成の必須機能にはしない。

```json
{
  "searches": [
    {
      "type": "vec",
      "query": "中断した処理を再開するとき、保存済み状態を再利用できる条件"
    },
    {
      "type": "lex",
      "query": "resume 再開"
    }
  ],
  "collections": ["oracle_docs"],
  "limit": 8,
  "candidateLimit": 40,
  "rerank": true
}
```

これは使用例であり、値を固定する仕様ではない。`limit` は返却件数、`candidateLimit` は再ランキング候補数で、別の予算である。確認した実装では先頭の sub-query の重みが大きい。[Q3]

QMD のツール説明は単純 `query` も勧めているため、エージェント向け案内では `searches` を使う経路を明示する。内部生成モデルを厳密に禁止する必要がある場合は、指示だけでなく入力制限が必要かを実装時に判断する。初期段階で汎用プロキシの開発まで前提にはしない。

### 6.2 MCP 設定注入

cmoc は既存の規約どおり、Codex の呼び出し単位で設定を渡す。ユーザーの `$CODEX_HOME/config.toml` を書き換えず、専用プロファイルや別の Codex 設定ファイルを新設しない。[C2]

注入する項目のイメージは次のとおり。これは説明用の TOML であり、このファイルを作成する指示ではない。

```toml
[mcp_servers.cmoc_docs]
command = "/absolute/path/to/qmd"
args = ["--index", "cmoc_docs", "mcp"]
cwd = "/absolute/path/to/worktree"
enabled_tools = ["query", "status"]

[mcp_servers.cmoc_docs.env]
QMD_CONFIG_DIR = "/absolute/path/to/qmd-config"
XDG_CACHE_HOME = "/absolute/path/to/qmd-cache"
```

Codex は stdio MCP の `command`、`args`、`cwd`、`env`、`enabled_tools` を提供する。実際には既存の cmoc の argv 構築経路から、適切な TOML 値として渡す。[Q7]

ツール許可リストは機能の整理であり、データへのアクセス制御の代わりではない。QMD には文書 resource もあるため、検索対象自体を許可範囲に閉じる。[Q3]

### 6.3 QMD のモデル設定

設定の構造は次の形を想定する。具体的な配布物・量子化形式を決定してから、検証済みローカルファイルへ置き換える。例の `--index cmoc_docs` に対応する設定名は `cmoc_docs.yml`。[Q9]

```yaml
models:
  embed: /absolute/path/to/Qwen3-Embedding-4B-<quant>.gguf
  rerank: /absolute/path/to/Qwen3-Reranker-4B-<quant>.gguf

collections:
  oracle_docs:
    path: /absolute/path/to/worktree/oracle/doc
    pattern: "**/*.md"
    ignore:
      - "**/INDEX.md"
```

この例の `oracle/doc` は初期対象の案であり、全 cmoc 利用先で固定すべき範囲ではない。`models.generate` は今回の必要構成に含めず、自動展開経路を使わない。

## 7. worktree・索引・サンドボックス

### 7.1 検索対象

検索対象は cmoc のインストール先ではなく、**その call の `work-root`** から決める。現行 cmoc の call-scoped path context と整合させる。[C2]

初期導入では正本仕様の Markdown を中心とし、生成済み INDEX.md、ログ、過去レポート、memo などは混在させない案が適切。oracle のソース側に委譲された定義は、従来の直接参照・文字列検索で引き続き確認する。

異なる worktree、異なる閲覧範囲の索引を取り違えない。特に `PURE_ORACLE_READ` 等の制限を、MCP の検索結果や resource 経由で迂回しない。`collections` フィルターをエージェントが正しく指定することだけに依存せず、その接続先の索引自体を許可範囲に限定する。

### 7.2 保存先と更新

設定・索引・実行キャッシュは Git 非追跡の cmoc 管理領域へ置く。例えば `<work-root>/.cmoc/gu/qmd/` が配置候補になるが、正確な配置は現行の管理領域の扱いに合わせて決める。

索引更新は検索のたびではなく、worktree の準備時や、対象文書を変更した作業の区切りで行う。基本となる QMD の操作は `update` と `embed`。同じ索引への更新処理は直列化する。[Q1]

同一範囲の検索 process は索引を再利用する案とするが、QMD は検索時にもキャッシュを書き込むため、完全な read-only DB として扱わない。DB の共有と更新の扱いは、採用バージョンの実装に合わせる。[Q8]

埋め込みモデルを変更した場合は文書ベクトルを再生成する。量子化、次元、入力形式、チャンク分割を変更する場合も、既存索引との互換性を確認し、異なるベクトル空間を混ぜない。

### 7.3 サンドボックス内での実行

QMD 本体とモデルの初回取得はセットアップに分離する。テスト時にモデルをダウンロードしたり、実行時のパッケージ取得に依存したりしない。

設定・DB・キャッシュの保存先は外側のサンドボックスから書き込み可能な場所へ向ける。モデルファイルは取得済みのものを参照する。モデル解決や推論ライブラリ初期化が追加取得・ビルドを起こさないことも確認する。

stdio に替えるだけでファイルアクセス制限が解消されるわけではない。通信経路と書き込み先を両方揃え、HTTP 待受やサンドボックスのネットワーク許可追加を要求しない。

## 8. QMD と Qwen3 の互換性に関する重要事項

### 8.1 入力形式と pooling

QMD には Qwen3-Embedding 専用の入力整形があり、検索語には `Instruct: ...\nQuery: ...`、文書には本文中心の形式を使う。Qwen の公式例でも検索用 instruction を用いる。[Q2][M1]

QMD のモデル系列判定は URI／パスの文字列に依存するため、ローカルモデルを `embed.gguf` のような汎用名へ変更せず、`Qwen3-Embedding` を識別できる名前を保つ。

Qwen3-Embedding は last-token pooling を前提とする。GGUF メタデータと実行ライブラリが適切に処理することが必要で、QMD 側に明示的な pooling 引数がないことだけでは、故障とも正常とも断定できない。[M4]

### 8.2 既知の品質低下報告

QMD Issue #714 には、2.5.3、Qwen3-Embedding-0.6B Q8_0、約1,000文書・20件の言い換え検索で、vector Recall@5 が0になったという報告がある。2026-09-25 の確認でも open。[Q5]

重要なのは、**pooling が原因という説明は報告者の仮説**であること。4B や現在の QMD で同じ問題が必ず発生する証拠ではなく、解消確認が済んだという証拠でもない。

このため、4B採用は維持しつつ、ベクトルが生成されるだけでなく、意味検索として明らかな関連・非関連を区別できることを接続時に確認する。

### 8.3 reranker 用 GGUF は配布物を選ぶ

`node-llama-cpp` の開発者は、Qwen3-Reranker 対応には llama.cpp `b6578` 以降で変換したモデルが必要と説明している。通常の生成モデルとして変換された古い GGUF を、名前だけで選ばない。[Q6]

4B の配布候補として、同開発者が案内している `giladgd/Qwen3-Reranker-4B-GGUF` がある。これは候補の出所が確認できたという意味であり、今回 cmoc／QMD 上の実行を確認したという意味ではない。[M5]

### 8.4 バージョンと tokenizer

QMD 参照コミットには、文書のチャンク分割に「実際に選択した埋め込みモデルの tokenizer」を使う修正が含まれる。CHANGELOG 上は未リリース項目である。[Q4]

バージョン番号だけで同じ挙動とみなさず、採用する QMD のタグまたはコミット、`node-llama-cpp`、モデルの revision・ファイル・チェックサムを記録する。

### 8.5 コンテキスト長と実際の処理

Qwen3 のモデル仕様上の32K入力と、QMD の実際の入力長は別である。調査時点の実装では埋め込みコンテキストの既定値は2048、再ランキングは4096。日本語や長い節では、チャンク分割と切り詰めの扱いが性能に影響する。[Q2]

モデルを変更しただけで、QMD が全文を32Kまで処理すると考えない。初期導入で上限を最大値へ引き上げることも前提にしない。

## 9. 4B + 4B の実行負担

Qwen 公式の Qwen3-Embedding-4B GGUF は、Q8_0 が約4.28 GB。これはファイル容量であり、VRAM 使用量ではない。[M4]

実行時には埋め込みモデル、reranker、各コンテキストなどが必要になる。stdio MCP の構成では、この負担が QMD process ごとに発生し得る。単一の4Bモデルが GPU に載ることから、複数 Codex call の同時実行まで安全とは判断できない。[Q2]

現行 QMD はモデル容量などからコンテキスト並列度を調整するが、別 process 間の GPU メモリ予約を一括管理するものではない。既存 cmoc の並列実行と両立するかを確認し、必要なら並列度に上限を設ける。

初期対処は、既存の並列度設定や QMD のコンテキスト数・候補数の調整を優先する。問題回避のために HTTP 共有サーバーを復活させたり、独自の推論共有基盤を追加したりしない。

また、QMD は reranker 初期化失敗時に再ランキングを省略する経路を持つ。**設定に4Bが書かれていることと、実際に4B reranker が動作したことを区別**し、警告や degradation を見落とさない。[Q2]

独自の検索品質ベンチマーク、評価データセット、大規模 A/B 試験は作らない。確認対象は、選択した構成が意図した処理を実行することに限定する。

## prompt parts を最適化する

- コンテキスト節約の一環として取り組みたい

## プロファイルベースでプロンプトブロックの順序を最適化する

- 今の順序が最適であるという確認はしていない
- 実際の過去の呼び出しパターンを元に順序を最適化したほうが良い
- シミュレーションは可能なはず
- 頻繁に変えるとキャッシュが効かなくなるので、サブコマンドで再計算とかだろうか

## 所見リストの編集をファイル経由にする

- 今は、編集前の所見リストを json でプロンプトに注入し、編集結果あるいは編集操作を Structured Output で受け取る形式にしている
- これをファイル経由にすれば、普通のソースコードの編集能力を活かせるので、所見リスト編集作業を無理無くこなせるはず
- その agent call で変化があったかも、ファイルのハッシュ値を見れば一目瞭然
- スキーマとそれを用いた機械的チェックの手段さえ与えればかなり有効なはず
- 読み書き規則のパターンが増えるかも

## 所見リストのマージと改善は別枠にしたほうが良い

- 改善作業には高価な高性能モデルが必要だが、高性能モデルは本当に高い
- 先に中性能モデルで所見リストをコンパクションして高性能モデルに渡す、高性能モデルによる改善は１～２周だけ、みたいな削減施策が必要

- quota poll の消費トークン数を削減
    - 多分 AGENTS.md とかを読みに行っていて、無駄に消費している

## 作業の停止性を良くしたい

- 反復オーケストレーションは停止性っぽい問題を抱えている
- e.g. Codex CLI が消化した以上に Codex CLI 自身が仕事を作る --> 反復のハードリミットいっぱいまで作業
- e.g. イテレーションを跨いで編集合戦を行う --> 循環参照的な構造が発生、反復のハードリミットいっぱいまで作業
- つまり、ハードリミットに達した時に、本当に作業が残っているのか、無駄な作業を無駄に作りまくっているのか、この区別が付かない
- この不安を払拭するために、工夫を入れたい
- 問題たりえるのは「Codex CLI が生成する仕事量」だけなので、ここを減らすしか無い

## デカい oracle ファイルを分割したい

    - 大きさじゃなくて、意味論を基準にしたほうが良いかも

    - Structured Output schema みたいに、 description として書き込むのが良さそう？
    - いや、そもそも json schema の専用の記法とか無いの？
