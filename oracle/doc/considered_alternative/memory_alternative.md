# AI-generated kaizen を自動的に次回実行へ反映しない理由

cmoc では、AI-generated kaizen を後続の Codex CLI 呼び出しへ自動注入する仕組みは採用しない。ここでいう kaizen は、AI が実行結果を振り返り、「次回以降はこう改善すべき」として生成する改善案を指す。

cmoc は、Codex CLI を外側から制御するための最小限の補助ツールである。そのため、動作の根拠を、仕様、入力、ログ、成果物として明示できる状態を重視する。AI が必要な情報へ明示的に到達できるよう、INDEX、oracle、ログ、実行成果物を整備し、暗黙記憶を持たせることは目指さない。

振り返りや改善案そのものを否定する判断ではない。問題は、検証・整理・人間による採用判断を経ずに、AI の改善案を次回以降の実行コンテキストへ継続的に混ぜる点にある。自動注入には、次の懸念がある。

- 仕様、ログ、一時的な失敗分析、思い込みが混ざり、どの指示が現在の挙動に影響するか追跡しづらくなる。cmoc の正本仕様断片である oracle とは別に、曖昧な準仕様が生まれ、仕様の単一性も損なわれる。
- AI による失敗原因の分析は常に正しいとは限らない。誤った分析を保存すると、同じ誤解が後続の実行でも参照され、誤診断が永続化される。
- ある実行で有効だった対処が、別の実行では逆効果になる可能性がある。蓄積した古い制約・実装・失敗・回避策から現在に合わない指示が混入し、それらを自動的に pruning することも難しい。

Codex CLI 本体にも memory 系の仕組みはあるが、スコープ、更新タイミング、要約、再生成、利用量消費などの運用上の難しさがある。cmoc が同種の仕組みを独自に持つと、別のレイヤーでも同じ問題を抱えることになる。
