# AI-generated kaizen を自動的に次回実行へ反映しない理由

cmoc では、AI-generated kaizen を後続の Codex CLI 呼び出しへ自動注入する仕組みは採用しない。ここでいう kaizen は、AI が実行結果を振り返り、「次回以降はこう改善すべき」として生成する改善案を指す。

振り返りや改善案そのものを否定しているわけではない。問題は、検証・整理・人間による採用判断を経ずに、AI の改善案を次回以降の実行コンテキストへ継続的に混ぜる点にある。

この仕組みは、AI が経験から学習するように見える。しかし実際には、異なる性質の情報が混ざり、曖昧な準仕様レイヤーが生まれやすい。混ざる情報には、仕様、ログ、一時的な失敗分析、思い込みがある。

cmoc は、Codex CLI を外側から制御するための最小限の補助ツールである。そのため、動作の根拠は、できるだけ明示された情報に置くべきである。根拠となる情報は、仕様、入力、ログ、成果物である。

AI-generated kaizen を自動注入すると、どの指示が現在の挙動に影響しているのか追跡しづらくなる。ある実行でたまたま有効だった対処が、別の実行では逆効果になる可能性もある。

AI による失敗原因の分析は、常に正しいとは限らない。誤った原因分析が kaizen として保存されると、以後の実行で同じ誤解が繰り返し参照され、誤診断が永続化される。

cmoc は、正本仕様断片として oracle を持つ。AI-generated kaizen が自動的に読まれると、oracle とは別の暗黙の仕様が生まれ、仕様の単一性が損なわれる。

kaizen を蓄積すると、古い情報が残り続ける。古い制約・実装・失敗・回避策によって、現在の状況に合わない指示が混入する。そうした情報を自動的に pruning することも難しい。

Codex CLI 本体にも memory 系の仕組みは存在するが、運用には難しさがある。難しい点には、スコープ、更新タイミング、要約、再生成、利用量消費などがある。cmoc が同種の仕組みを独自に持つと、別のレイヤーでも同じ問題を抱えることになる。

cmoc は、AI に暗黙記憶を持たせることを目指さない。AI が必要な情報へ明示的に到達できる状態を目指すべきである。そのために、INDEX、oracle、ログ、実行成果物を整備する方がよい。
