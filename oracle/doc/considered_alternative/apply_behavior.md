# `cmoc realization refactor` についての「やらなかった話」

## 修正点リスト完成後の作業計画立案をやらなかった理由

### 概要

- 「修正点リスト完成 --> 作業計画立案 --> 計画に基づく修正作業」という流れを検討した
- 高度な推論を要する計画立案を独立させ、トークン消費を抑えることを狙っていた
- しかし、この方針は採用しなかった

### 不採用の理由

- 実装では想定と異なる事態が起きやすい。事前の計画と実態が乖離すると、余計な思考にトークンを費やすリスクがある
- 修正漏れには、後続の調査ループで修正点を再び列挙することで対応できると考え、修正精度の向上だけを計画立案の採用理由にはしなかった


## 所見リストの並列リストアップをやらなかった理由

### 概要

- realization refactor の前身となった orchestration では、調査対象 file を先に列挙し、各 file を起点にした所見リストアップを並列実行する方針を検討していた
- ファイルごとの所見リストを連結したあと、agent call で所見リスト全体を改善する
- 改善後の所見リストに含まれる所見 1 件ごとに、独立した agent call で修正作業を行う
- さらに、一時的な処理 queue を表すダーティフラグで、次に調査すべき file を管理する想定だった

### 不採用の理由

- 所見の調査時と適用時では、realization file の状態が異なる可能性がある
- 複数ファイルから同じ所見が重複して見つかる。その重複を取り除くために追加の agent call が必要となり、トークン消費が増える
- 並列リストアップは、ファイル間の依存関係を agent call の外側で先に固定するので、実際の修正作業で見つかる関連ファイルや影響範囲を反映しづらい
- 所見リスト全体の改善ループは、重複や False-Positive の除去には使えるが、所見を正規化するためだけの独立した orchestration と prompt を増やす
- 所見 1 件ごとの修正は、複数所見が同じ実装箇所へ関係する場合に、agent call 間の文脈分断とコミット粒度の細分化を招く
- そのため、「列挙を先に広げ、改善してから所見単位で直す」流れは採用せず、永続的な調査要求に従って file 単位で所見調査と反映作業を進める方式にした。現行の調査要求と処理単位は、`{{cmoc-root}}/oracle/doc/app_spec/sub_command/realization_refactor.md` の「refactor state」と「refactor loop」を正本とする。
