
# `cmoc` における `{{work-root}}` 上の `INDEX.md` の扱い

## 概要

- `cmoc` は、`{{work-root}}` 配下の大半のディレクトリに `INDEX.md` を配置する。対象は後述する
- `cmoc` が自動でインデクシングするため、人間が `INDEX.md` を書く必要はない

## `INDEX.md` 配置対象ディレクトリ

- `{{work-root}}` 配下のディレクトリを再帰的に列挙する
- 以下のディレクトリは配置対象から除外する
    - `.` から始まるディレクトリ
    - `.gitignore` の対象
    - `{{work-root}}/memo`
    - バイナリファイル

## 目次作成対象ファイル・ディレクトリ

- `INDEX.md` と同階層のファイル・ディレクトリを列挙する
- 以下のファイル・ディレクトリは目次作成対象から除外する
    - `.` から始まるファイル・ディレクトリ
    - `.gitignore` の対象
    - `{{work-root}}/memo`
    - `INDEX.md`
    - バイナリファイル

## `INDEX.md` のフォーマット

- ファイル・ディレクトリ 1 件ごとに、以下のフォーマットで「目次情報」を用意する
    ```markdown
    # `{{ファイル・ディレクトリ名}}`

    ## Summary

    {{ルーティング先ファイル・ディレクトリの説明}}

    ## Read this when

    {{どんな作業・質問・変更のときに、このファイル・ディレクトリを読むべきか}}

    ## Do not read this when

    {{逆に、このファイル・ディレクトリを読まなくて良い・読んではいけないケース}}

    ## hash

    {{この目次情報を生成するにあたって参照したファイル・ディレクトリとそのハッシュ}}
    ```
- `{{ルーティング先ファイル・ディレクトリの説明}}`
    - 箇条書きとする
    - ファイル・ディレクトリに何が書いてあるか・入っているかを書く
- `{{どんな作業・質問・変更のときに、このファイル・ディレクトリを読むべきか}}`
    - 箇条書きとする
    - AI が対象を読むべき条件を明示する
- `{{逆に、このファイル・ディレクトリを読まなくて良い・読んではいけないケース}}`
    - 箇条書きとする
    - AI が「関連しそう」という理由だけで過剰に読まないよう、対象を読む必要がない条件や、読んではいけない条件を書く
- `{{この目次情報を生成するにあたって参照したファイル・ディレクトリとそのハッシュ}}`
    - 箇条書きとする
    - ファイルの場合
        - ファイルの内容である文字列から計算したハッシュ値 (SHA-256) を書く
    - ディレクトリの場合
        - 直下の目次作成対象ファイル・ディレクトリをリポジトリ相対パスの辞書順で安定ソートし、各エントリについて `type + '\0' + relative_path + '\0' + content_hash + '\n'` を連結した UTF-8 文字列から SHA-256 を計算する

## 目次情報の意味要件

目次情報は、AI agent が対象本文を読む前に、その対象へ進むべきかを判断するための routing 情報とする。対象本文の代替となる詳細説明にしてはならない。

`Summary`、`Read this when`、および `Do not read this when` は、次の要件を満たす。

- 人間が読む自然言語部分は原則として日本語とする。識別子、path、command、hash、および引用は元の表記を維持してよい。
- 目次情報は対象の現在内容だけを根拠とする。対象外の責務を記載すると AI agent が不要な対象を読む原因になるため、対象外の責務または将来の用途を推測で追加しない。
- 対象が担う責務と、同階層の別対象ではなくその対象へ進む条件を示す。
- 関連しそうという理由だけで対象へ進ませる広すぎる条件を避ける。
- 対象を読まなくてよい境界、またはより直接的な参照先がある場合の境界を示す。
- ファイル名、ディレクトリ名、hash、出力形式、または Structured Output schema の項目などは、cmoc が機械的に補う情報である。これらを自然言語へ混ぜると routing 判断に必要な意味情報が薄まるため、routing 用の意味情報へ混ぜない。

## `INDEX.md` による routing

- agent は、作業対象に近い階層の `INDEX.md` から必要な本文を選ぶ。対象領域を推定できない場合は `{{work-root}}/INDEX.md` を起点とする。
- `Read this when` と `Do not read this when` を選択に使用し、関連候補を総当たりで読む前に対象を絞る。
- `INDEX.md` は本文の代替にせず、意味または最新状態を判断する場合は選択した本文を根拠とする。
        
## インデクシングの仕様

### 処理対象

1. 配置対象ディレクトリは前述のルールで機械的に列挙する
2. 列挙されたディレクトリを「深い方から」順番に処理する
    - 例：`{{work-root}}/parent/INDEX.md` で `{{work-root}}/parent/child` の目次情報を作成するために `{{work-root}}/parent/child/INDEX.md` を閲覧する可能性がある
    - そのため、子ディレクトリ側を先に最新の状態にする
3. インデクシングによって発生した git 未コミット差分を自動コミットする
    - インデクシングの呼び出し 1 回につき、1 つのコミットにまとめること
    - コミット対象は「`INDEX.md` の差分」に限定すること
    - インデクシング開始時点での `INDEX.md` 以外の既存差分はコミット対象から除外すること
    - インデクシング開始時点での `INDEX.md` の既存差分はコミット対象に混ざってもよいものとする
    - 既存差分が存在した場合も処理は続行する

### ディレクトリ１つごとの処理

- `INDEX.md` が存在しなければ新規に作成する
- `INDEX.md` 内の目次情報に不備がないか確認する
    - ファイルシステム上に存在するファイル・ディレクトリに対応する目次情報がなければ、新規に作成する
    - 存在しないファイル・ディレクトリの目次情報は削除する
    - 記録されているハッシュ値と実際のハッシュ値が一致しない場合は、目次情報を削除して再生成する

### 目次情報の生成方法

- 目次情報の生成対象 1 件ごとに、独立した agent call を行う
- agent call は本書の「目次情報の意味要件」に従う。正確な prompt part、文面、workload 固有の起動パラメータ、およびその選択理由は、`{{cmoc-root}}/oracle/src/oracle/acp_builder/indexing/index_entry.py` の `build_indexing_index_entry_parameter` へ委譲する
- 「ファイル・ディレクトリ名」「ハッシュ値」などの機械的に処理可能な部分は cmoc が責任を持つ

## 目次情報生成の並列実行

- 基本方針
    - 目次情報生成のための `codex exec` 呼び出しは、可能な限り並列に実行する
    - ただし、並列化によって、前述の「深い方から原則」を破ってはいけない
- 並列化規則
    - 同じ `INDEX.md` 内のエントリ同士は並列化してよい
    - 祖先・子孫の関係にない `INDEX.md` 同士は並列化してよい
        - 例：`/path/to/A/INDEX.md`, `/path/to/B/INDEX.md` は並列化してよい（祖先・子孫の関係にないため）
        - 例：`/path/to/A/INDEX.md`, `/path/to/A/B/INDEX.md` は並列化してはいけない (`/path/to/A/B/INDEX.md` を先に処理する)

## インデクシングの実行条件・タイミング

- インデクシングは `AgentCallParameter.run_indexing_preflight == True` の場合だけ実行する
- 本命の agent call を実行する直前にインデクシングを実行する

## `INDEX.md` が最新に保たれている状態でメンテナンス処理が実行されたら

- 機械的チェックによって、最新状態であることが確認される
- その結果、Codex CLI による目次生成は一切実行されない
