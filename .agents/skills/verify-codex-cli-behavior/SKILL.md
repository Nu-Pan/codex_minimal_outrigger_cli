# Codex CLI への依存をソースと実測で確かめる

アプリが依存する Codex CLI の挙動を、対象版のソースと安全な実測で確かめる。アプリの要求と CLI との連携コードを読み、要求を満たすかどうかの判断を左右する挙動を特定する。そのうえで、その挙動を確かめるために必要な範囲を調べる。

後方互換性は原則保持しない。明示要件がある場合だけ保つ。明示要件は、利用者の指示、AGENTS.md、正本仕様から確認する。対象版で要求を満たすための処理と、旧版を支える互換処理やフォールバックを区別し、後者は明示要件がある場合だけ追加・保持する。

## 対象版を確定する

調査するソースは、アプリが宣言するコミット、または固定されたバージョンを優先して選ぶ。特定できなければ、アプリが実際に起動する CLI の版やロックファイルを確認する。バージョンを基に調査する場合は、対応する `openai/codex` のリリースタグ `rust-v{{version}}` が指すコミットを特定する。

タグを根拠にする場合は、タグが指すコミットオブジェクトの SHA を取得する。注釈付きタグにはタグ自体の SHA もあるため、`^{commit}` またはリモートの peeled reference を使ってコミットの SHA を確かめる。

それでも対象を特定できなければ、最新の安定版を調査用に代用する。その際、代用した理由と、対象環境の挙動は未確認であることを示す。なお、プレリリース版は、利用者やアプリが指定した場合に使う。

## 根拠を確認する

重要な挙動は、対象リビジョンで製品として実際に動作するコードを読んで確認し、必要な呼び出し元と実装先をたどる。そのうえで、対象コミットに根拠となるファイルと行が存在することを確かめる。その根拠を参照できるように、判断を支える行範囲に絞って、次の形式の恒久リンクを示す。

```text
https://github.com/openai/codex/blob/{{commit-sha}}/{{source-path}}#L{{start-line}}-L{{end-line}}
```

`{{commit-sha}}` は省略しない40桁のコミット SHA とする。公式文書やテストは、コードの解釈を補うために使う。一方、アプリが満たすべき要求は利用者の指示とアプリの正本仕様から確認し、CLI の内部実装を理由にそれらの要求を書き換えない。また、現在の実装を確認できても、将来の互換性や公開契約を保証する根拠にはしない。

ソースから読み取った挙動が、文書の説明や実測した挙動と異なる場合は、調査したソースのリビジョンと、文書や実測の対象版・条件を照合する。不一致が残れば、ソース、文書、実測のそれぞれから確認した事実を分けて示す。なお、非公開のサーバー側処理については、CLI 側で確認できる範囲までを根拠として扱う。

## 実測で要求への適合を確かめる

安全に実行できる場合は、ソースの確認で前提にしたバージョン、プラットフォーム、設定にそろえ、アプリの呼び出し経路から重要な挙動を観測する。直接 CLI を起動する測定では、引数、作業ディレクトリ、環境などの差がアプリでの結果を変えないか確かめる。

実測の結果は、アプリの正本が認める入力と利用条件に照らして判断する。検証用の条件での成功だけで実際の利用を保証せず、失敗を正しく通知できることと、必要な機能が使えることを分けて確かめる。CLI の実行前提によって正本が認める利用を拒否する場合も、不整合として扱う。

実測には一時的な作業ディレクトリと非機密の入力を使う。認証や外部への作用が必要な操作は、既存の権限とリポジトリの規則に従う。

一方、実測できなければ、その理由と判断への影響を示す。いずれの場合も、ソースから確認した内容と実測した内容を区別する。

重要な挙動について、対象版と実行環境で要求を満たすかを評価する。バージョンの固定や起動時の確認などは、確認した挙動と実行環境をそろえるために必要な場合に選ぶ。一つの対策や検証で複数の挙動を扱える場合は、その対策と検証結果を共用する。

フォールバックを採用する場合は、現在の要求に必要な障害時の処理か、明示された旧版対応かを確かめ、処理が失敗する条件と利用者への通知内容を明らかにする。

## 検証結果を反映して報告する

対応範囲は、元の依頼とセッションで認められた作業から判断する。アプリの実装・変更では、対象版で要求を満たす単純な構成へ不整合を解消し、不要になった関連する旧版用の処理や説明を削除する。明示された互換性要件があれば、その範囲の対応と検証を含める。一方、検証や根拠の記録だけの依頼では、アプリの挙動や契約を変更せず、確認できた事実と不足を示す。レビューだけの依頼ではファイルを変更しない。

根拠を示す際は、アプリがその挙動に依存する理由と、ソースの確認や実測で分かったことを説明する。そのうえで、調査したソースのリビジョンと実測時の条件を示し、ソースの確認と実測が同じ条件に基づくかを読み手が確かめられるようにする。また、確認方法と残る不確実性を明らかにする。

根拠を成果物へ残す依頼では、詳細を既存の設計文書など一箇所へ集約し、CLI との連携コードの必要な箇所から参照する。その際、文書を新設する場合もリポジトリの配置に合わせる。

最終報告では、不一致の根拠と影響、対応内容、検証結果を伝え、詳細を残した場所を案内する。参照先がなければ、報告自体に、実際に動作するコードへの恒久リンクと必要な根拠を載せる。

レビューでは、挙動の根拠を追い、対象版で要求を満たすかを確かめる。記載場所の好みや、明示要件のない旧版対応の欠如を挙動上の不整合とみなさない。重要な挙動やその根拠が未確認の場合や、明示要件を満たせない場合は、理由と判断への影響を報告する。旧版対応を含める場合は、根拠となる明示要件も示す。実際に動作するコードを確認できない重要な挙動が残る場合は、検証完了としない。
